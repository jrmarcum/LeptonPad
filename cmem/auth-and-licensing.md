# Auth, Roles, and Licensing

**Clerk** supplies identity. **Neon Postgres** holds roles, packs, and codes. The **LeptonPad API**
on Deno Deploy sits between them and is the only thing that touches the database.

The browser never holds a database credential and never reaches Postgres. Every entitlement call
carries a Clerk session JWT as a bearer token, and the API derives the user id from that token alone.

## Role hierarchy

| Role    | Can do                                                                                |
| ------- | ------------------------------------------------------------------------------------- |
| `super` | Everything — create any section, access **all** packs regardless of ownership, admin. |
| `pro`   | Create/edit any section block + use owned purchased template packs.                   |
| `demo`  | Same as `pro`, expires 30 days from trial start.                                      |
| `free`  | Use purchased section template packs only; **cannot create blank sections**.          |

`canCreateSection()` (`auth.ts`) returns true for `super`/`pro`/`demo`. `hasPack(packId)` returns true
for `super` or when `packId ∈ ownedPackIds`.

**Expiry degrades server-side.** `get_my_role()` downgrades a `demo` **or** a `pro` row to `free` when
`trial_expires_at` is in the past. The client never computes expiry — a client clock is not a trust
boundary.

**A user needs no `user_roles` row.** Absent row means `free`. Clerk has no signup hook writing one,
and nothing depends on one existing — see the trap noted under `get_my_role` below.

## Database schema (`db/schema.sql`)

Five tables. **No RLS policies and no `auth.users`** — Clerk owns identity, and no client connects to
Postgres, so the API is the boundary rather than row-level security.

| Table           | Shape                                                                                                           |
| --------------- | --------------------------------------------------------------------------------------------------------------- |
| `user_roles`    | `user_id` **text** PK (a Clerk id, `user_2abc…`), `role` (checked enum), `trial_started_at`, `trial_expires_at` |
| `license_codes` | `code` PK (uppercase), `grants_role`, `grants_pack_id`, `valid_days`, `used_by`, `used_at`                      |
| `section_packs` | `id` slug PK, `name`, `description`                                                                             |
| `pack_secrets`  | `pack_id` PK, `secret` (random 32-byte hex, generated by `create_section_pack`)                                 |
| `user_packs`    | `(user_id, pack_id)` PK, `redeemed_via`, `purchased_at`, `expires_at`                                           |

Two CHECK constraints do real security work:

- `license_codes.grants_role` is restricted to **`'pro'` or `'demo'`** — a code can never grant
  `super`. Verified 2026-08-13; see [`security-model.md`](security-model.md).
- `one_grant` enforces that a code grants **exactly one** of a role or a pack, never both.

`valid_days = 0` means perpetual.

## The three functions

All take `p_user_id` as their **first argument**, supplied by the API from a verified JWT.

**`get_my_role(p_user_id)`** → `{ role, trial_expires_at, pack_ids }`. Applies expiry degradation,
then aggregates `user_packs` filtered by `expires_at is null or expires_at > now()`.

⚠️ **It must never early-return when the role row is missing.** Ownership lives in `user_packs`, a
separate table — a `free` user with no role row can still own packs, and an early return made those
packs invisible. That was a live bug on 2026-08-13. The empty case must also use
`array[]::text[]`, not `'{}'`, or the JSON carries the _string_ `"{}"` instead of `[]`.

**`redeem_license_code(p_user_id, p_code)`** → `{ success, message, role?, pack_id? }`. Claims the
code and marks it used **in a single UPDATE … RETURNING**, so two concurrent redemptions of one code
cannot both succeed. Then upserts either `user_roles` (setting `trial_started_at` only for `demo`)
or `user_packs`. This is the **only** path in the API that writes to `user_roles`.

**`get_pack_key(p_user_id, p_pack_id)`** → base64 key or null. Ownership/super check first, then
`encode(hmac(p_user_id, pack_secret, 'sha256'), 'base64')`. See
[`security-model.md`](security-model.md).

## Admin helpers — run locally, never exposed over HTTP

| Task                                                  | Does                                                         |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| `deno task promote`                                   | Lists Clerk accounts with their current roles                |
| `deno task promote <email> [role]`                    | Looks the account up in Clerk by email, upserts `user_roles` |
| `deno task db:check`                                  | 10-assertion regression test of the whole chain              |
| `select create_section_pack('slug','Name','desc')`    | Creates a pack **and** generates its secret                  |
| `select * from mint_license_codes(10,'pro',null,365)` | Mints codes in `XXXX-XXXX-XXXX-XXXX` form                    |

`create_section_pack` will not rotate an existing secret (`on conflict do nothing`) — rotating one
would orphan every pack already sold under the old key.

## License codes

- Format `XXXX-XXXX-XXXX-XXXX`, uppercase hex, minted by `mint_license_codes`.
- Case-insensitive on redemption (`rawCode.trim().toUpperCase()` in `license.ts`, `upper()` again in
  SQL).
- One-time use — enforced by `used_by is null` in the claiming UPDATE, not by the client.
- `showRedeemCodeDialog()` (`license.ts`) is the modal; Enter submits, Escape and backdrop-click
  cancel. On success `redeemLicenseCode()` calls `refreshEntitlements()` so the sidebar re-renders
  without a reload.
- `accessSummary()` produces the sidebar string: "Full access (super)" / "Pro — all features" /
  "Demo trial active" / "N template pack(s)" / "Free — no packs".

## ⚠️ The Clerk instance is a DEVELOPMENT instance — origins must be allowlisted

Verified 2026-08-13 via `GET https://api.clerk.com/v1/instance`:

```json
{ "environment_type": "development", "allowed_origins": [...] }
```

Its registered domain is `devoted.lab-77.lcl.dev` (frontend API
`devoted-lab-77.clerk.accounts.dev`), a local-development domain. **`allowed_origins` was `null`, and
sign-in on the deployed site failed with "Password is incorrect."** — a credential error that says
nothing about the real cause, which is why this cost an hour. The same password worked on localhost.

Fixed by adding the production origin:

```bash
SK=$(grep '^CLERK_SECRET_KEY=' .env.api | cut -d= -f2- | tr -d '\r\n' | sed 's/^"//; s/"$//')
curl -X PATCH -H "Authorization: Bearer $SK" -H 'Content-Type: application/json' \
  -d '{"allowed_origins":["https://leptonpad.jrmarcum.deno.net","http://localhost:5173"]}' \
  https://api.clerk.com/v1/instance
```

**Any new origin — a custom domain, a preview URL — must be added to this list or sign-in fails
there with a misleading error.**

💡 `.env.api` quotes its values. Deno's `--env-file` strips the quotes; a shell `cut` does not, so a
raw `curl` with the extracted key returns `clerk_key_invalid` and looks like a bad key. Strip the
quotes and the `\r` from CRLF.

### ⛔ The allowlist was NOT enough — a dev instance cannot serve the deployed site

Adding the origin did not fix sign-in. Probing Clerk's Frontend API directly returns the real reason,
which the app's "Password is incorrect." never revealed:

```json
{
  "code": "dev_browser_unauthenticated",
  "message": "Unable to authenticate this browser for your development instance."
}
```

Development instances authenticate the browser through a **dev-browser handshake** against
`*.clerk.accounts.dev`. That works on localhost and does not survive on a deployed domain. Clerk's own
docs put it plainly: development instances have "a more relaxed security posture and are **not
suitable for production workloads**", and are capped at **100 users** with no data transfer between
instances.

**So live sign-in is blocked until there is a Clerk _production_ instance**, which requires all of:

| Requirement          | Detail                                                |
| -------------------- | ----------------------------------------------------- |
| A domain you control | `*.deno.net` cannot work — DNS records are needed     |
| CNAME records        | FAPI hosted at `clerk.<yourdomain>`                   |
| Production keys      | `pk_live_` / `sk_live_` replacing the `pk_test_` pair |
| Own SSO credentials  | Clerk's shared dev OAuth credentials are dev-only     |

Until then: **auth works locally, and the deployed site serves everything except sign-in.** The rest of
the app — canvas, math engine, plots, save/load — is unaffected, because the backend is only a gate.

## Sign-up flow — Clerk uses a code, not a link

`signUp()` returns `needsVerification: true` when Clerk wants the emailed **6-digit code**. The login
modal then hides the email and password fields, shows a one-time-code input, and switches the button
to "Confirm Email"; `verifyEmailCode()` completes it and signs the user in.
`Backend.verifyEmailCode()` is optional on the interface because a link-based provider would not
need it.

⚠️ **Clerk's free tier fixes session lifetime at 7 days.** Cached role and pack keys mean sheets keep
opening offline, but users re-authenticate weekly to refresh entitlements. Accepted 2026-08-13 as a
reasonable security posture.

## Offline-first client cache (`auth.ts`)

Clerk persists its own session, so a signed-in user stays signed in across restarts. On top of that:

| Key              | Contents                                                   |
| ---------------- | ---------------------------------------------------------- |
| `lp_role`        | The role string from the last successful `getMyRole()`     |
| `lp_packs`       | JSON array of owned pack ids                               |
| `lp_pk_<packId>` | Base64 key material, so encrypted templates render offline |

`initAuth()` loads the backend, restores the session, and syncs entitlements — falling back to the
cache on **any** throw, because a network failure must not lock a user out of their own sheets.
`clerk.load()` failing (offline) is caught and the app boots anyway.

`_clearSession()` on logout clears `lp_role` and `lp_packs` but **deliberately keeps `lp_pk_*`** so a
logout/re-login on the same device still renders the user's own projects. An accepted tradeoff,
recorded in [`security-model.md`](security-model.md).

## One-time setup

1. Create a Neon project; run `db/schema.sql` against it (needs `pgcrypto`).
2. Create a Clerk application; enable email + password.
3. `cp .env.api.example .env.api` — `DATABASE_URL`, plus `CLERK_JWT_KEY` (PEM public key, networkless
   verification) **or** `CLERK_SECRET_KEY` (JWKS fetch). Set `ALLOWED_ORIGINS` including
   `http://localhost:5173`.
4. `cp .env.example .env` — `CLERK_PUBLISHABLE_KEY` and `LP_API_URL`.
5. Deploy `api/main.ts` to Deno Deploy with the same server-side variables.
6. Sign up through the app, then `deno task promote <your-email>`. The Clerk user id does not exist
   until the account does.
